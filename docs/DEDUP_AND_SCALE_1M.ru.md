# 🧬 Дизайн дедупликации и масштаба до 1M фактов

> **Дата:** 2026-05-31 · **Канон:** [TRUTH_AND_RINGZERO_CANON.ru.md](TRUTH_AND_RINGZERO_CANON.ru.md) · **Схема ингеста:** [INGEST_SCHEMA_50K.ru.md](INGEST_SCHEMA_50K.ru.md)
> **Аудит-основа:** находки M3 (порядок-зависимая кластеризация), M5 (дедуп-скан 5000 строк), C1/C2 (split-brain).
>
> Цель: память, которая растёт **50K → 1M фактов** оффлайн, **не теряя проверенное** и **не плодя дубли**,
> при этом оставаясь быстрой. Каждое решение помечено «на что влияет».

---

## 0. Два врага на масштабе

1. 🔴 **Тихая порча** — дубли (ID или смысловые) и потеря фактов незаметно накапливаются. На 5K — терпимо, на 1M — необратимо.
2. 🔴 **Комбинаторный взрыв** — наивный дедуп сравнивает каждый факт с каждым: O(N²). При 1M это 10¹² сравнений — невозможно.

> **На что влияет:** без решения обоих база на 1M либо сгниёт от дублей, либо встанет от медлительности. Этот документ закрывает оба.

---

## 1. Различение: дубль ≠ подтверждение (ядро модели)

| Случай | Что делать | Эффект на confidence |
|--------|-----------|----------------------|
| Тот же смысл, **тот же источник** | 🗑️ отбросить (точный дубль) | без изменений |
| Тот же смысл, **другой источник** | 🔗 слить → **corroboration** | ↑ повысить (независимое подтверждение) |
| Противоположный смысл (X vs не-X) | ⚔️ НЕ сливать → `contradicts`-ребро | разрешается резолвером |
| Похожий, но **новый аспект** | ✅ хранить как отдельный факт | — |

🔑 Это не «удаление похожего». Это **слияние тождественного и усиление подтверждённого**. Полярность (X vs не-X) проверяется до слияния (фикс `02507a2` уже есть).

## 2. Три слоя дедупа

```
Слой A — СБОР (markdown → факты)     : уникальность ID + namespace + verifier ✅
Слой B — ИНГЕСТ, точный дубль        : claim_dedup_key, индексированный lookup O(log N)
Слой C — ИНГЕСТ, смысловой дубль     : эмбеддинги + ANN + порог + полярность → corroboration
```

### 🅰️ Слой A — сбор (уже работает)
- `scripts/verify_world_skills.py` — машинная проверка уникальности ID (0 дублей доказано, не заявлено).
- Namespace `domain.subdomain.term` + блокировка по домену предотвращает коллизии при ручном вводе.
- **На что влияет:** ловит дубли ДО попадания в граф — дешевле всего.

### 🅱️ Слой B — точный дубль при ингесте (фикс M5)
**Проблема:** `find_fact_id_by_claim_dedup` ([memory.py:529](core/memory.py)) при промахе индекса сканирует только последние **5000 строк** → в БД >5000 дубль не находится.
**Решение:**
1. `claim_dedup_key = sha256(normalize(claim))` — нормализация: lowercase, схлопывание пробелов, удаление пунктуации, опц. лемматизация.
2. Колонка `claim_dedup_key` с **UNIQUE-индексом** → lookup за O(log N), **без скана**.
3. Миграция: backfill ключа для существующих фактов.
4. Убрать `LIMIT 5000` целиком — индекс делает скан ненужным.

**На что влияет:** 🎯 точные дубли ловятся при ЛЮБОМ размере БД за миллисекунды. Прямой фикс находки M5 — прерэквизит 1M.

### 🅲 Слой C — смысловой дубль (фикс M3 + масштаб)
**Проблема:** жадная кластеризация ([semantic_dedup.py](core/semantic_dedup.py)) — O(N²) и **порядок-зависима** (M3): результат меняется между прогонами.

**Решение — ANN вместо попарного сравнения:**
1. **Эмбеддинг** каждого факта (локальная модель, напр. MiniLM 384-dim — оффлайн).
2. **ANN-индекс** (HNSW / sqlite-vec / FAISS): поиск k ближайших за **O(log N)**, не O(N).
3. При ингесте: для нового факта найти ближайших → если cosine ≥ порог **И** та же полярность **И** (тот же источник → дубль / другой → corroboration).
4. **Детерминизм (фикс M3):** канонический представитель кластера = факт с min `fact_id` (стабильно), не «первый по порядку».

```
ingest(fact):
  key = sha256(normalize(claim))
  if exact_hit(key):           return merge_exact()        # слой B
  neighbors = ann.query(embed(fact), k=10, domain=fact.domain)
  for n in neighbors sorted by fact_id:                    # детерминизм
      if cosine(fact,n) >= 0.86 and same_polarity(fact,n):
          if same_source(fact,n): return drop_duplicate()
          else:                   return corroborate(n)    # ↑confidence
  return store_new(fact)
```

**На что влияет:** 🎯 смысловые дубли ловятся за O(log N) и **детерминированно** — фикс M3 + масштабируемость до 1M.

## 3. Блокировка (blocking) — как избежать O(N²)

Сравнивать только внутри **домена/namespace**, а не со всей базой:
```
candidate_set = ANN.query(vec, k=10, filter: domain == fact.domain)
```
- 1M фактов / ~60 доменов ≈ 16K на домен → пространство сравнения падает ~60×.
- ANN внутри домена → реальные сравнения на факт: ~10, не 1M.

**На что влияет:** ⚙️ превращает невозможные 10¹² сравнений в линейный по объёму ингест.

## 4. Физика масштаба (бюджеты)

| Объём | Что ломается без мер | Меры | Память эмбеддингов |
|-------|---------------------|------|--------------------|
| **10K** | ничего | как есть | ~15 МБ |
| **100K** | дедуп-скан M5, retrieval `SELECT *` | слой B (индекс), FTS5, ANN | ~150 МБ |
| **1M** | O(N²) дедуп, граф-обход, RAM | блокировка, ANN на диске, лимиты графа | ~1.5 ГБ (float32) / **384 МБ (int8)** |

- **Эмбеддинги 1M:** 1M × 384 × 4 байта = **1.46 ГБ**; int8-квантизация → **~384 МБ** (приемлемо оффлайн).
- **ANN-индекс:** HNSW с mmap на диск — не держит всё в RAM.
- **SQLite до 1M:** для одного пользователя **достаточно** при правильных индексах. Postgres/Neo4j НЕ нужны оффлайн.
- **L0-кэш (128 записей):** на 1M бесполезен — полагаться на page-cache SQLite; L0 оставить для горячих фактов сессии.

**На что влияет:** 🌐 подтверждает: 1M оффлайн на ноутбуке реален. Главный ресурс — ~400 МБ на эмбеддинги + диск под ANN.

## 5. Retrieval на 1M (не сканировать!)

Сейчас `_lexical` Core-3 делает `SELECT * FROM facts` + токенизация каждого claim — O(N) на запрос. На 1M это секунды.

**Гибрид на индексах:**
```
score = α·FTS5(lexical) + β·ANN(semantic) + γ·graph_proximity + δ·recency
```
- **FTS5** (уже есть `ngram_index` в V8.6) — лексический поиск по индексу, не скан.
- **ANN** — семантические соседи за O(log N).
- **graph_proximity** — рекурсивный CTE с **лимитом глубины ≤3 и фанаута** (иначе обход взрывается).
- Кандидаты от FTS5+ANN (top-200), затем точное ранжирование только по ним.

**На что влияет:** ⚡ ответ за десятки мс при 1M вместо секунд скана.

## 6. Консолидация (offline, sleep-worker)

Не весь дедуп — в реальном времени. Ночной проход:
- **Повторная кластеризация** дрейфующих near-duplicate (детерминированно, по ANN).
- **Перерасчёт corroboration** и confidence.
- **Резолвер противоречий** (trust-aware, ДО promotion — фикс M4).
- **Decay/forgetting:** понизить salience редких/старых, но **no-DELETE** проверенного.

**На что влияет:** 🍂 «умное забывание» без потери истины; база остаётся релевантной и чистой по мере роста.

---

## 7. Требования детерминизма и идемпотентности

| Требование | Почему |
|-----------|--------|
| `get_all_facts` со стабильным `ORDER BY` (фикс M2/H2) | дедуп и резолвер не должны зависеть от порядка строк |
| Канонический представитель = min `fact_id` | один и тот же результат между прогонами |
| Повторный ингест того же факта = no-op | идемпотентность, безопасные повторы |
| Дедуп vs `seen`-множество, не vs «текущий ответ» | сходимость без зацикливания |

**На что влияет:** 🔁 повторные заливки и ночные проходы дают одинаковый результат — доверие к процессу.

---

## 8. Метрики (verify, don't assert)

Отслеживать на каждом этапе роста:
- **dup_rate** — % смысловых дублей (цель: ~0, измерять выборочной ручной проверкой ANN-пар).
- **corroboration_rate** — доля фактов с ≥2 источниками (рост = здоровье базы).
- **retrieval_latency_p95** — задержка поиска (цель: <100 мс на 1M).
- **ingest_throughput** — фактов/сек при батч-заливке.
- **orphan_facts** — факты без источника (должны быть Observed/gap, не Validated).

## 9. Фазы реализации (приоритет + влияние)

| Фаза | Что | Приоритет | На что влияет |
|------|-----|:---------:|---------------|
| **D1** | Слой B: `claim_dedup_key` + UNIQUE-индекс, убрать `LIMIT 5000` (фикс M5) | 🔴 P0 | точные дубли при любом N; прерэквизит >5K |
| **D2** | Стабильный `ORDER BY` в `get_all_facts` + канон. представитель (фикс M2/M3) | 🔴 P0 | детерминизм дедупа и резолвера |
| **D3** | Retrieval на FTS5 + пагинация (убрать `SELECT *`-скан) | 🟠 P1 | скорость поиска на 100K+ |
| **D4** | Слой C: локальные эмбеддинги + ANN-индекс + блокировка по домену | 🟠 P1 | смысловой дедуп O(log N) до 1M |
| **D5** | Consolidation: trust-aware резолвер ДО promotion (фикс M4) + decay | 🟡 P2 | умное забывание, чистота на росте |
| **D6** | int8-квантизация эмбеддингов + ANN на диске | 🟡 P2 | бюджет RAM ~400 МБ на 1M |

> D1–D2 нужны **уже сейчас** — до того, как база перерастёт 5K (сейчас 5.2K). D3–D4 — на горизонте 50K. D5–D6 — к 1M.

## 10. Что НЕ делать
- ❌ Не сравнивать каждый факт с каждым (O(N²)) — только ANN внутри домена.
- ❌ Не удалять проверенные факты ради «дедупа» — инвариант no-DELETE; дубль сливается, не стирается.
- ❌ Не переходить на серверную БД ради 1M оффлайн — SQLite+индексы достаточно для одного пользователя.
- ❌ Не доверять `duplicate_ids: 0` без инструмента — только вычислять (verify).
- ❌ Не делать весь дедуп синхронно в запросе — тяжёлое в ночную консолидацию.

---

*Связь с каноном: дедуп — это applied-форма принципа «Graph = Truth». Один факт = один узел; подтверждения усиливают, противоречия разрешаются, ничего проверенного не теряется. Этот документ — план, как удержать этот инвариант на пути к миллиону.*
