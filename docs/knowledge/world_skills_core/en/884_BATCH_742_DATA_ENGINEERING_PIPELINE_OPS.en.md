|---|---|---|---|---|
| dataeng.ops.etl_vs_elt | ETL vs ELT — Architecture Patterns | METHOD | ETL (Extract, Transform, Load): трансформация до загрузки в хранилище. ELT (Extract, Load, Transform): загрузка raw данных → трансформация в хранилище (SQL или Spark). ELT преимущества: облачные DW (Snowflake, BigQuery) = дешёвое хранение + дорогой compute on demand. Medallion Architecture: Bronze (raw) → Silver (cleaned) → Gold (aggregated). | ELT + dbt: современный стандарт для analytical pipelines. |
| dataeng.ops.spark_rdd_dataframe | Apache Spark — RDD vs DataFrame | METHOD | Apache Spark: RDD (Resilient Distributed Dataset): иммутабельная распределённая коллекция. DataFrame: структурированные данные (Catalyst optimizer). Dataset: типизированный DataFrame (Scala). Lazy evaluation: только при action (collect, write, count). Wide transformations (join, groupBy): shuffle между partition. Narrow (map, filter): без shuffle. | Catalyst query optimizer: автоматическая оптимизация → 10-100× быстрее ручного RDD. |
| dataeng.ops.kafka_consumer_group | Kafka — Consumer Groups | METHOD | Apache Kafka: Producer → Topic → Consumer. Partition: единица параллелизма. Consumer Group: каждый partition → только одному consumer. Offset: позиция в partition. Auto.offset.reset: earliest или latest. Replication factor: 3 (производство). ISR (In-Sync Replicas). At-least-once vs at-most-once vs exactly-once semantics. Schema Registry (Avro/Protobuf). | Kafka lag: отставание consumer от producer → Alert при lag > threshold. |
| dataeng.ops.dbt_transformation | dbt — Data Build Tool | METHOD | dbt (data build tool): трансформации в SQL с версионированием. Models: SELECT statements (materialized as table/view/incremental/snapshot). Staging → Intermediate → Mart. Tests: unique, not_null, accepted_values, relationships. Documentation: YAML описание. Lineage: граф зависимостей. dbt Cloud vs Core. CI/CD pipeline для SQL transformations. | Incremental materialization: только новые данные + MERGE strategy = efficiency. |
| dataeng.ops.data_quality_great_expectations | Data Quality — Great Expectations | METHOD | Great Expectations: Python-библиотека для data quality тестирования. Expectations: expectations = тесты на данных (column to be not null, values to be between X-Y). Expectation Suite. Checkpoints: запуск тестов в pipeline. Data docs: HTML отчёт о качестве. Profile: автоматическое создание expectations из данных. Integration: Airflow, Spark, dbt. | Data contract: явное соглашение между producer и consumer о schema/quality. |
| dataeng.ops.snowflake_architecture | Snowflake — Multi-Cluster Architecture | METHOD | Snowflake: разделение storage (S3/Azure Blob/GCS) и compute. Virtual Warehouses: независимые compute clusters. Автоскейлинг. Time Travel: запрос исторических данных (до 90 дней). Zero-Copy Cloning: мгновенная клонировка без дублирования данных. Snowpipe: автоматическая загрузка при появлении файлов в S3. Failsafe: 7 дней после Time Travel. | Snowflake Credit: единица вычислений. XS = 1 credit/ч, 3XL = 128 credits/ч. |
| dataeng.ops.lakehouse_delta_lake | Delta Lake — ACID Transactions | METHOD | Delta Lake (Databricks): ACID транзакции поверх object storage (S3, ADLS). Delta Log: JSON-файлы с историей изменений. Compaction (OPTIMIZE): объединение мелких файлов. ZORDER: кластеризация по часто фильтруемым полям. Time Travel: VERSION AS OF, TIMESTAMP AS OF. Schema evolution: MERGE INTO. Change Data Feed (CDF). | Delta table: решает «small files problem» в Parquet/Spark. |
| dataeng.ops.airflow_dag | Airflow — DAG Structure | METHOD | Apache Airflow: DAGs (Directed Acyclic Graphs) = workflows. Operators: PythonOperator, BashOperator, SparkSubmitOperator, SQLExecuteQueryOperator. Task dependencies: >>. XCom: обмен данными между tasks. Scheduler + Web Server + Executor (LocalExecutor, CeleryExecutor, KubernetesExecutor). SLA (Service Level Agreement): алерты при опоздании задач. | Airflow не = data processing tool (orchestration only). |
| dataeng.ops.schema_evolution | Schema Evolution — Strategies | METHOD | Эволюция схемы: добавление новых колонок (backward compatible). Удаление колонок: breaking change (downstream impact). Переименование: breaking. Изменение типа: breaking. Stategies: schema-on-read (Avro), schema-on-write (Parquet). Avro schema registry: управление совместимостью. BACKWARD, FORWARD, FULL compatibility modes. | Schema drift: неожиданное изменение данных от источника → автоматическое обнаружение важно. |
| dataeng.ops.cdc_change_data_capture | CDC — Change Data Capture | METHOD | CDC (Change Data Capture): отслеживание изменений в source database → streaming обновления. Методы: Log-based CDC (Debezium: читает WAL PostgreSQL, binlog MySQL — наиболее надёжный). Trigger-based. Timestamp-based (polling — не real-time). Debezium → Kafka → Flink/Spark → target. Use case: real-time data sync, event sourcing. | Log-based CDC: не влияет на source database performance. |
| dataeng.ops.data_warehouse_modeling | Data Warehouse — Kimball vs Inmon | METHOD | Kimball (Bottom-Up): dimensional modeling — fact tables + dimension tables. Star schema. OLAP queries через denormalized structure. Conformed dimensions. Bus architecture. Inmon (Top-Down): corporate information factory. Normalized 3NF subject area. ETL → Data Warehouse → Data Marts. Комбинация: Vault + star schema. | One Big Table (OBT): flat wide table = простейшая но повторы и memory overhead. |
| dataeng.ops.partitioning_strategy | Data Partitioning — Strategies | METHOD | Партиционирование данных: Static partitioning: date, region, category. Dynamic partitioning: по ключу из данных. Hive partitioning: директории в HDFS/S3 (date=2024-01-01/). Partition pruning: SQL engine читает только нужные партиции. Over-partitioning: too many small files → metadata overhead. Bucket (Hash partitioning): для равномерного распределения при joins. | Partition key selection: наиболее часто используемый filter = key (date, region). |
| dataeng.ops.data_contracts | Data Contracts — Standards | METHOD | Дата-контракты: явное соглашение между data producers и consumers. Компоненты: schema (поля, типы), SLAs (freshness, availability), semantics (определения), ownership, quality expectations. OpenDataContract (ODC): открытый стандарт. Бизнес = producer + consumer = данные — как API (SaaS model for data). Data Mesh: domain ownership + data as product + self-serve platform. | Без контрактов: молчаливые breaking changes → down-stream failures без warning. |
| dataeng.ops.batch_vs_streaming_latency | Batch vs Streaming — Trade-offs | METHOD | Batch (пакетная обработка): высокая throughput, высокая latency (минуты-часы). Micro-batch (Spark Structured Streaming): каждые 1-5 мин. Streaming (Flink, Kafka Streams): sub-second latency. Lambda Architecture: batch + streaming layers. Kappa Architecture: только streaming. Complex Event Processing (CEP): паттерны в потоке событий. | Latency requirement: определяет архитектуру. Near real-time (<1 мин): micro-batch. Real-time (<100 мс): streaming. |
| dataeng.ops.row_vs_columnar_storage | Storage Format — Parquet vs CSV | METHOD | Форматы хранения данных: CSV: текстовый, все типы как strings, нет сжатия, нет scheme. Parquet: columnar — эффективен для аналитических запросов (читает только нужные колонки). Snappy/ZSTD compression. ORC: похожий (Hive ecosystem). Avro: row-based + schema evolution (streaming). Delta/Iceberg/Hudi: table formats поверх Parquet. | 10× speed improvement: Parquet vs CSV для аналитических queries (column pruning). |
| dataeng.ops.orchestration_comparison | Orchestration — Airflow vs Prefect vs Dagster | METHOD | Orchestration tools: Airflow: доминирует, DAG-based, Python, сложный Setup. Prefect: более Pythonic, better for dynamic workflows, Prefect Cloud. Dagster: asset-centric (data assets = first-class), strong data lineage, type system. Temporal: workflow engine для long-running business processes. Mage: modern Airflow alternative. | Asset-based vs task-based: Dagster = assets (что производишь), Airflow = tasks (что делаешь). |
| dataeng.ops.star_schema_design | Star Schema — Fact Table Design | METHOD | Звёздная схема: Fact table (транзакции, события): измеримые метрики (quantity, amount). Foreign keys к dimensions. Additive vs semi-additive vs non-additive facts. Slowly Changing Dimensions (SCD): Type 1 (overwrite), Type 2 (new row with version), Type 3 (new column). Degenerate dimension: в fact table (order_number). | SCD Type 2: самый распространённый для исторического анализа (customer address changes). |
| dataeng.ops.data_lineage_tools | Data Lineage — OpenLineage | METHOD | Прослеживаемость данных (Data Lineage): откуда данные, куда идут, через какие преобразования. OpenLineage: открытый стандарт метаданных. Marquez: open-source lineage server. Apache Atlas, DataHub, Collibra: enterprise tools. Column-level lineage: детальнее чем table-level. Impact analysis: что сломается при изменении upstream? | Регуляторное требование (GDPR): знать где персональные данные хранятся и используются. |
| dataeng.ops.flink_stateful | Apache Flink — Stateful Streaming | METHOD | Flink: distributed stream processing. State: keyed state (per-key), operator state. Checkpoints: асинхронное сохранение состояния (для восстановления). Exactly-once: через 2-phase commit + Flink checkpoints. Event time vs Processing time: event time + watermarks (handle late data). Window types: Tumbling, Sliding, Session. | Backpressure: downstream медленнее upstream → Flink автоматически снижает скорость. |
