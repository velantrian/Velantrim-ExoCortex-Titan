| itops.incident_management_flow | Управление инцидентами — процесс ITIL | PROCESS | Управление инцидентами (ITIL). Инцидент = незапланированное прерывание или снижение качества IT-услуги. Жизненный цикл: 1) Идентификация (мониторинговое оповещение или пользовательский билет), 2) Логирование (тикет в системе ITSM — ServiceNow/Jira Service Management), 3) Категоризация (категория/подкатегория для маршрутизации и отчетности), 4) Приоритизация (Воздействие × Срочность: P1 — отключено для всех, немедленно; P2 — деградировано для всех; P3 — отдельный пользователь; P4 — низкое воздействие, запланировать), 5) Первоначальная диагностика (L1: известная проблема? Соответствие КБ? если да — решение), 6) Эскалация (функциональная — L2/L3, иерархическая — управление при SLA под угрозой), 7) Исследование и диагностика (L2/L3 — логика, трассировка, воссоздание), 8) Разрешение и восстановление (исправить + проверить), 9) Закрытие (подтверждение пользователем того, что сервис восстановлен). SLA: Время ответа (P1 <15 мин, P2 <30, P3 <2), Время разрешения (P1 <4 часа, P2 <8, P3 <24 часа). После инцидента: при P1/P2 — рассмотрение крупного инцидента (MIR), анализ первопричин, запись о проблеме, если основная причина неизвестна. | Разница между Incident и Problem: Incident — «сервис упал, восстанови», Problem — «почему он упал? предотврати повторение». Incident management = пожарная команда, Problem management = пожарная инспекция. |
| itops.change_management_cab | Управление изменениями — процесс CAB | METHOD | Управление изменениями (ITIL). Change = любое добавление/модификация/удаление чего-либо в IT-инфраструктуре. Типы: Standard (pre-approved, низкий риск — замена мышки, ежемесячный Windows update), Normal (требует review и approval), Emergency (для исправления критического инцидента — ускоренный процесс). CAB (Change Advisory Board): регулярный meeting (еженедельно) рассматривает pending normal changes. Change record содержит: описание, risk assessment (impact + probability), backout plan (как откатить если что-то пойдёт не так), test plan (как проверено что изменение работает), maintenance window (когда — обычно ночью/выходные, с уведомлением пользователей). Approval: технические команды + бизнес (service owner). Post-implementation review (PIR): достигнуты ли цели? неожиданные последствия? CAB может revoke approval если PIR показывает проблемы. Культура: «change is guilty until proven innocent» (по умолчанию изменение = риск, оно должно доказать свою безопасность). | Без change management: «админ обновил production в пятницу вечером и ушёл, в понедельник всё лежит». Change success rate (KPI): >95% successful (без инцидентов). Unauthorized changes: немедленный review + disciplinary action (это серьёзно). |
| itops.problem_management_rca | Управление проблемами — анализ первопричин | METHOD | Поиск корневой причины инцидентов. Техники: 1) 5 Whys (спрашивать «почему?» 5 раз: сервер перегрелся → почему? вентилятор сломался → почему? preventive maintenance не сделано → почему? CMMS задача была закрыта без выполнения → почему? нет контроля качества), 2) Ishikawa/Fishbone (категории: People, Process, Technology, Environment, Measurement), 3) Fault Tree Analysis (нисходящая логика: отказ системы → какие комбинации отказов компонентов могут к нему привести?), 4) Kepner-Tregoe (сравнивает что ЕСТЬ с тем чего НЕТ: проблема на сервере A но не на идентичном B → что разного между ними?). Продукты: Known Error (документированная проблема + workaround до постоянного решения) и RFC (Request for Change для постоянного решения). KPI: MTBF (время между отказами), % repeat incidents (<5%), number of known errors resolved. Proactive Problem Management: анализ trend-ов (растущее число инцидентов с конкретным приложением → investigation до major failure). | Наиболее частые коренные причины: 1) Изменения (70-80% инцидентов вызваны изменениями), 2) Единичные точки сбоя, 3) Истощение мощностей, 4) Человеческая ошибка (пробелы в обучении/процессе, а не индивидуальная вина). |
| itops.backup_3_2_1_rule | Резервное копирование — правило 3-2-1 и тестирование | METHOD | Стратегия резервного копирования. 3-2-1: 3 копии данных, на 2 разных типах носителей, 1 копия off-site (географически удалена) + air-gapped (недоступна online) для защиты от ransomware. Типы: Full (все данные, долго, много места), Incremental (только изменения с последнего backup — быстрее, но restore требует full + все incrementals), Differential (изменения с последнего full — restore = full + последний differential). Retention: GFS (Grandfather-Father-Son): ежедневные (son, 7-14 дней), еженедельные (father, 4-5 недель), ежемесячные (grandfather, 12 месяцев), ежегодные (7-10 лет для compliance). RPO (Recovery Point Objective) = максимально допустимая потеря данных по времени (1 час? 24 часа?). RTO (Recovery Time Objective) = максимальное время восстановления сервиса (4 часа? 24 часа?). Backup testing: регулярное тестовое восстановление (минимум quarterly) — backup, который не тестирован, НЕ считается работающим. | Ransomware изменил backup стратегию: immutable backups (WORM — write once read many, нельзя изменить/удалить даже admin) + air-gap (физическое отключение backup storage от сети между backup windows). Без этого ransomware шифрует production + находит backup storage и шифрует/удаляет бэкапы. |
| itops.disaster_recovery_plan | План аварийного восстановления — структура и тестирование | METHOD | DR Plan: документ, описывающий восстановление IT после катастрофы (site loss, earthquake, fire, cyberattack). Содержит: 1) Scope (какие системы покрыты, приоритеты восстановления — Tier 1: mission-critical <4 часа, Tier 2: important <24 часа, Tier 3: non-essential <1 неделя), 2) Activation criteria (кто и при каких условиях объявляет disaster), 3) Roles (Disaster Recovery Coordinator, Technical Recovery Teams, Communications Lead), 4) Recovery procedures (пошаговые инструкции для каждой системы: как восстановить из backup, как переключить трафик на DR site), 5) Contact list (актуальные телефоны всех участников, включая вендоров), 6) Alternate site (hot site — готов к работе за часы, стоит дорого; warm site — оборудование есть, данные восстанавливаются — дни; cold site — пустое помещение, всё привозить — недели). 7) Testing: tabletop (проговаривают по сценарию), simulation (частичное восстановление), full cutover (реальное переключение на DR site). Частота: tabletop annually, simulation bi-annually, full cutover 1-3 года. | DR plan, который не тестировался full cutover — НЕ план. 90% компаний, теряющих data centre без DR, выходят из бизнеса в течение 2 лет (National Archives). Пандемия — другой тип disaster: не site loss, а loss of staff и невозможность физического доступа в офис. |
| itops.sre_error_budget | SRE — Бюджет ошибок и управление трудозатратами | METHOD | Site Reliability Engineering (Google). Ключевые концепции: SLI (Service Level Indicator — измеренная метрика: доступность 99.95%, latency P99 <200ms), SLO (Service Level Objective — целевое значение SLI), SLA (Service Level Agreement — контракт с клиентом: если нарушено → penalties). Error Budget = 100% − SLO (например, SLO 99.95% → error budget 0.05% = 43 минуты downtime в месяц). Когда error budget не исчерпан — команда может пушить новые фичи (принимать риски). Когда исчерпан — заморозка фич, все ресурсы на reliability. Toil (рутинная ручная работа, не создающая долгосрочной ценности: ручной перезапуск сервисов, ответы на однотипные тикеты): цель <50% времени инженеров. Автоматизация (runbooks → self-healing automation). Blameless post-mortems: после инцидента — что пошло не так, как процесс/система это допустили (не КТО виноват). Action items: предотвратить этот класс инцидентов. | Error budget: демократизирует конфликт dev (хочет фичи) и ops (хочет стабильности). Dev знает: если мы сделаем фичу и она вызовет incidents → потратим error budget → следующий релиз отложен. |
| itops.it_asset_management | Управление ИТ-активами — жизненный цикл | METHOD | Управление IT-активами (оборудование и ПО). Жизненный цикл оборудования: Запрос → Утверждение → Закупка → Получение → Маркировка (бирка актива, штрих-код) → Развертывание (установка, назначение пользователю) → Техническое обслуживание (ремонт, модернизация) → Вывод из эксплуатации (безопасное удаление данных — NIST 800-88, 3-проходное или технологическое уничтожение HDD/SSD — измельчитель, размагничиватель) → Утилизация (переработка электронных отходов, R2/e-Stewards) сертификат). CMDB (база данных управления конфигурацией): отношения между CI (элементами конфигурации) — сервер A размещает приложение B, зависит от базы данных C. Обнаружение: агенты/сканирование сети автоматически находят и обновляют данные. Управление лицензиями на программное обеспечение: соответствие (не использовать больше ограничений, чем куплено — риск аудита со стороны Microsoft/Oracle с предложениями штрафами), сбор урожая (перераспределение неиспользуемых значений), сверка (ежегодный отчёт вендору). KPI: использование ресурсов (% использования по сравнению с простоем), цикл обновления (ноутбуки 3–4 года, серверы 4–5 лет), соблюдение требований по утилизации (100 % безопасное удаление). | Утерянный/украденный ноутбук: если HDD не зашифрован (BitLocker/FileVault) → data breach → notification costs $150-200/record. MDM (Mobile Device Management — Intune, Jamf): удалённая очистка потерянного устройства. |
