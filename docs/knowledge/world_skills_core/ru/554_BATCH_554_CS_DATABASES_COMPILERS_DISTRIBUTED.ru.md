| cs.databases.acid | ACID-транзакции | INVARIANT | Aтомарность (всё или ничего), Cогласованность (ограничения), Iзоляция (промежуточные состояния не видны другим), Dолговечность (закоммиченное не теряется). Обеспечивается: WAL (write-ahead log), блокировками, MVCC. | Банковский перевод: списание + зачисление должны быть атомарны → либо оба, либо ни одного. |
| cs.databases.isolation_levels | Уровни изоляции транзакций | VARIANT | Read Uncommitted (грязное чтение), Read Committed, Repeatable Read (фантомы?), Serializable (строжайший — эквивалентно последовательному выполнению). Аномалии: грязное чтение, неповторяемое чтение, фантомы. | PostgreSQL: по умолчанию Чтение зафиксировано, сериализуется через сериализуемую изоляцию моментальных снимков (SSI). MySQL InnoDB: Повторяемое чтение (фантомы не выполняются через пробелы в блокировках). |
| cs.databases.mvcc | Многоверсионное управление параллелизмом (MVCC) | METHOD | Каждая транзакция видит снапшот БД на момент начала (snapshot isolation). Запись не блокирует чтение (читатель не ждёт писателя). Старые версии кортежей — в табличном пространстве, очистка VACUUM (PostgreSQL). | PostgreSQL, Oracle, InnoDB. Писатели могут конфликтовать на одном кортеже — first-committer-wins (откат проигравшего). |
| cs.databases.b_tree_db | Деревья B+ в базах данных | INVARIANT | Индекс: сбалансированное дерево с высокой степенью ветвления (fanout 100-1000+). Все данные в листьях, внутренние узлы — только ключи. Листья связаны списком для range scan. Глубина 2-4 для миллиардов строк. | Первичный индекс (кластеризованный): данные отсортированы по ключу (InnoDB — primary key определяет физический порядок). Вторичный: ссылка на первичный ключ. Covering index: все столбцы запроса в индексе → без обращения к таблице. |
| cs.databases.query_optimizer | Оптимизатор запросов | METHOD | Парсинг SQL → логический план (реляционная алгебра) → физический план (алгоритмы: hash join, merge join, index scan, seq scan). Оптимизатор на основе стоимости (cost-based): кардинальность (оценка числа строк через статистику), стоимость операций. | EXPLAIN ANALYZE — план выполнения. Seq Scan vs Index Scan: seq быстрее для >10% таблицы. Nested Loop vs Hash Join vs Merge Join — выбор по размеру и сортированности. |
| cs.databases.sharding | Шардинг и репликация базы данных | METHOD | Шардирование: горизонтальное разделение по ключу (хэш, диапазон, directory-based). Репликация: master-slave (один пишет, многие читают), multi-master (конфликты!). CAP: Consistency, Availability, Partition tolerance — выбирай два для сетевого раздела. | Cassandra (AP — окончательная согласованность), MongoDB (CP на первичном голосовании), асинхронная репликация PostgreSQL (читающие реплики). |
| cs.compilers.phases | Этапы компиляции | INVARIANT | Frontend: лексический анализ (лексемы), синтаксический (AST), семантический (типы). Middle-end: промежуточное представление (IR — LLVM IR, GCC GIMPLE), оптимизации (независимые от архитектуры). Backend: выбор инструкций, распределение регистров, генерация машинного кода. | LLVM: модульный дизайн — язык компилируется в LLVM IR, оптимизируется, генерируется код целевой архитектуры. Rust, Swift, Julia — все на LLVM. |
| cs.compilers.regex_parsing | Лексический анализ и регулярные выражения | METHOD | Сканер: регулярные выражения → NFA (алгоритм Томпсона) → DFA (конструкция подмножеств) или напрямую. Flex — генератор сканера. Токены: keyword, identifier, number, string, operator. | [a-zA-Z_][a-zA-Z0-9_]* — идентификатор. Регулярные языки — тип 3 в иерархии Хомского (автомат без памяти). Контекстно-свободные — тип 2 (парсинг). |
| cs.compilers.context_free_grammar | Контекстно-свободные грамматики и синтаксический анализ | INVARIANT | CFG: правила A→α (нетерминал → строка терминалов/нетерминалов). BNF (Backus-Naur Form). LL(k): левый разбор, сверху-вниз, предиктивный (ANTLR). LR(k): правый разбор, снизу-вверх, сдвиг/свёртка (Yacc/Bison). | LL(1): по первому терминалу определяем правило. Левая рекурсия (A→Aα) недопустима для LL парсера. LR парсеры — мощнее (DCFL), ручной код сложнее. |
| cs.compilers.type_checking | Проверка типов и вывод | METHOD | Статическая vs динамическая типизация. Hindley-Milner вывод типов (ML, Haskell): унификация типовых переменных. Алгоритм W (Damas-Milner). Let-polymorphism (let id x = x — полиморфна ∀α.α→α). | Rust: заимствование (borrow checker) — проверка времён жизни и владения на этапе компиляции (безопасность памяти без GC). |
| cs.compilers.optimizations | Оптимизация компилятора | METHOD | Встраивание, постоянное свертывание (3+4→7), устранение мертвого кода, развертывание цикла, инвариантное к циклу движение кода, устранение общего подвыражения. Форма SSA (Статическое одиночное присвоение: каждая переменная применяется ровно один раз). | -O2 vs -O3: -O3 агрессивнее (векторизация, unrolling), может увеличить размер кода. Profile-Guided Optimization (PGO): компиляция → профайлинг → рекомпиляция с реальными данными о горячих путях. |
| cs.distributed.cap_theorem | Теорема CAP | INVARIANT | Брюэр (2000), формально доказана Гилбертом и Линчем (2002): распределённая система при сетевом разделе (P) выбирает между согласованностью (C) и доступностью (A). Без раздела — можно и C, и A. На практике всё — постоянный выбор. | CP-системы (Zookeeper, etcd — лидер, кворум, жертва доступности при разделе). AP (Cassandra, DynamoDB — всегда отвечают, eventual consistency). CA (одиночная БД — нет распределения). |
| cs.distributed.paxos | Протокол Паксосского консенсуса | METHOD | Роли: proposers, acceptors, learners. Фаза 1 (prepare/обещание), Фаза 2 (accept/фиксация). Кворум: >½ акцепторов. Гарантия безопасности (только одно значение за номером предложения) + живучесть (если достаточно узлов живы). Лампорт (1989). | Zookeeper (Zab — Paxos-like), etcd (Raft — более понятный аналог Paxos). Многие системы используют Paxos для leader election и конфигурации. |
| cs.distributed.raft | Плот Консенсус | METHOD | Leader (один), followers (реплицируют), candidates (выборы). Term — логическое время. Сердцебиения (heartbeat) от лидера. Лидер реплицирует записи → большинство подтверждает (committed) → apply. Таймеры выборов 150-300 мс. | etcd, Consul, TiKV, CockroachDB — все используют Raft. Проще для понимания и реализации, чем Paxos (явный лидер, логи репликации). |
| cs.distributed.two_phase_commit | 2-фазная фиксация (2 ПК) | PROCESS | Протокол атомарного коммита распределённой транзакции. Фаза 1: координатор спрашивает всех участников — готовы? Phase 2: все готовы → COMMIT; хоть один нет → ROLLBACK. | Недостаток: блокировка при отказе координатора (участники ждут, держат блокировки). 3PC решает блокировку ценой дополнительных сообщений. |
